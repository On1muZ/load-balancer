# lb — HTTP балансировщик нагрузки на Go

Reverse proxy, который распределяет входящие HTTP-запросы между пулом бэкендов. Поддерживает несколько алгоритмов балансировки, активные health-check'и и горячую перезагрузку списка нод без рестарта.

## Возможности

- **5 алгоритмов балансировки**: round robin, weighted random, least connections, weighted least connections, power of two choices (P2C).
- **Health checker**: периодически опрашивает все ноды (`GET /`), выводит упавшие из ротации и возвращает восстановившиеся. Ответ `2xx`/`3xx` — нода жива.
- **Hot reload нод**: файл `nodes.json` отслеживается через fsnotify (с debounce 300 мс). Новые ноды добавляются, удалённые убираются, у существующих обновляется вес — счётчики соединений и метрики при этом сохраняются. Если файл невалиден, остаётся текущий список, а в лог пишется ошибка с номером строки и колонки.
- **Lock-free выбор бэкенда**: список живых нод хранится в `atomic.Pointer` и пересобирается только при изменении состояния, счётчики соединений — атомики.
- **Graceful shutdown** по `SIGINT`/`SIGTERM` с выводом метрик по каждой ноде (число запросов, аптайм).
- **Структурные логи** (`log/slog`): цветной текст в `dev`, JSON в `prod`.

## Алгоритмы

| Значение `ALGORITHM`          | Как выбирает ноду                                                                 |
|-------------------------------|------------------------------------------------------------------------------------|
| `round_robin`                 | По кругу, веса игнорируются                                                       |
| `weighted_random`             | Случайно, с вероятностью пропорциональной весу                                    |
| `least_connections`           | Нода с наименьшим числом активных соединений                                      |
| `weighted_least_connections`  | Нода с наименьшим отношением `активные соединения / вес`                          |
| `p2c`                         | Берёт две случайные ноды и выбирает менее нагруженную с учётом веса               |

## Структура проекта

```
cmd/lb/                 точка входа
internal/
  backend/              модель бэкенда, пул нод, загрузка nodes.json
  balancer/             HTTP-хендлер и реализации алгоритмов
  config/               конфигурация из переменных окружения
  health_checker/       периодическая проверка нод
  logger/               настройка slog
  metrics/              счётчики запросов и история health-событий
  proxy/                httputil.ReverseProxy с пулом буферов
  transport/            настроенный http.Transport (keep-alive пул к бэкендам)
  watcher/              отслеживание изменений nodes.json
config/nodes.json       список нод
test/backend.go         тестовый бэкенд для локальных экспериментов
```

## Быстрый старт

### Docker Compose

```bash
docker compose up --build
curl localhost:9000
# hello from backend 8001
```

Поднимается балансировщик на `:9000` и пять тестовых бэкендов. В `config/nodes.json` изначально прописаны четыре из них; `backend-5` можно добавить на лету — просто отредактируйте файл, директория `config/` смонтирована в контейнер:

```json
{ "ip": "backend-5:8004", "weight": 100 }
```

Тестовый бэкенд отвечает с задержкой 10 мс, а на порту `8000` — 100 мс, чтобы было видно, как алгоритмы обходят медленную ноду.

### Локально

```bash
go build -o bin/lb ./cmd/lb
go build -o bin/backend ./test/backend.go

./bin/backend 8000 & ./bin/backend 8001 &

cat > nodes.local.json <<'EOF'
{ "nodes": [ { "ip": "127.0.0.1:8000", "weight": 10 }, { "ip": "127.0.0.1:8001", "weight": 100 } ] }
EOF

ALGORITHM=p2c NODES_FILE_PATH=./nodes.local.json ./bin/lb
```

## Конфигурация

Все параметры задаются переменными окружения. Таймауты — в секундах.

| Переменная                    | По умолчанию | Описание                                                  |
|-------------------------------|--------------|-----------------------------------------------------------|
| `ALGORITHM`                   | —            | **Обязательная.** Алгоритм балансировки (см. таблицу выше) |
| `NODES_FILE_PATH`             | —            | **Обязательная.** Путь к файлу с нодами                    |
| `APP_ENV`                     | `dev`        | `dev` — debug-логи текстом, `prod` — info-логи в JSON      |
| `HTTP_PORT`                   | `9000`       | Порт балансировщика                                       |
| `HEALTH_CHECKER_INTERVAL`     | `1`          | Интервал между проверками нод                              |
| `HEALTH_CHECKER_TIMEOUT`      | `1`          | Таймаут одной проверки                                    |
| `SERVER_READ_HEADER_TIMEOUT`  | `5`          | `http.Server.ReadHeaderTimeout`                           |
| `SERVER_READ_TIMEOUT`         | `30`         | `http.Server.ReadTimeout`                                 |
| `SERVER_WRITE_TIMEOUT`        | `60`         | `http.Server.WriteTimeout`                                |
| `SERVER_IDLE_TIMEOUT`         | `120`        | `http.Server.IdleTimeout`                                 |
| `MAX_HEADER_BYTES`            | `1048576`    | Максимальный размер заголовков запроса                    |

### Формат `nodes.json`

```json
{
  "nodes": [
    { "ip": "backend-1:8000", "weight": 10 },
    { "ip": "backend-2:8001", "weight": 100 }
  ]
}
```

- `ip` — `host:port` без схемы (используется `http://`), должен быть уникальным;
- `weight` — целое число от 1 до 2³¹−1;
- неизвестные поля и мусор после JSON-объекта считаются ошибкой.

## Нагрузочное тестирование

Замеры сделаны [vegeta](https://github.com/tsenart/vegeta) 2026-09-23.

**Стенд:** AMD Ryzen 5 5600H (6 ядер / 12 потоков), 16 ГБ RAM, Linux. Балансировщик (`APP_ENV=prod`, `ALGORITHM=p2c`), 4 тестовых бэкенда (задержка ответа 10 мс) и vegeta запущены **на одной машине** через loopback.

### Фиксированный rate (open-loop)

```bash
echo "GET http://127.0.0.1:9000/" | vegeta attack -rate=10000 -duration=20s -timeout=5s | vegeta report
```

| Rate, rps | Throughput | Success | p50     | p95      | p99      | max      |
|-----------|------------|---------|---------|----------|----------|----------|
| 5 000     | 4 997      | 100%    | 11.2 ms | 17.5 ms  | 32.7 ms  | 113 ms   |
| 8 000     | 7 996      | 100%    | 11.1 ms | 15.3 ms  | 24.2 ms  | 84 ms    |
| 10 000    | 9 995      | 100%    | 11.3 ms | 19.4 ms  | 28.6 ms  | 76 ms    |
| 11 000    | 10 996     | 100%    | 11.0 ms | 116 ms   | 241 ms   | 748 ms   |
| 12 000    | 7 670      | 83.9%   | 2.7 s   | 9.0 s    | 10.1 s   | 15.9 s   |

Минимальная задержка ≈ 10.3 мс — это задержка самого бэкенда, то есть накладные расходы балансировщика на p50 составляют ~1 мс.

### Максимальная пропускная способность (closed-loop)

```bash
echo "GET http://127.0.0.1:9000/" | vegeta attack -rate=0 -max-workers=1000 -duration=15s | vegeta report
```

| Воркеров | Throughput | Success | p50     | p99     |
|----------|------------|---------|---------|---------|
| 200      | 12 653     | 100%    | 12.4 ms | 44.7 ms |
| 1 000    | 22 972     | 100%    | 37.4 ms | 87.8 ms |

### Итог

- **~10 000 rps** — стабильно, без ошибок, p99 < 30 мс;
- **~11 000 rps** — без ошибок, но хвост задержек растёт (p99 ≈ 240 мс);
- **~23 000 rps** — пиковая пропускная способность при 1000 одновременных соединениях, без ошибок.

Упираемся в CPU машины, а не в балансировщик как таковой: на 12k rps все 12 потоков загружены полностью — vegeta занимает ~5 ядер, балансировщик ~4–5, бэкенды ~2.5. Дальше vegeta в open-loop режиме открывает всё больше соединений (до ~10k) и заканчиваются эфемерные порты (`bind: address already in use`). Если вынести генератор нагрузки и бэкенды на отдельные машины, цифры будут выше.

> Между прогонами стоит дождаться, пока сокеты в `TIME_WAIT` освободятся (`ss -tan state time-wait | wc -l`), иначе следующий прогон упрётся в нехватку портов и покажет заниженный результат.
